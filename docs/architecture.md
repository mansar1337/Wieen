# Wieen: архитектура

```
хост                                        агент (в процессе клиента)
┌───────────────────────────┐              ┌──────────────────────────────┐
│ wieen CLI / wieen-compile │              │ agent (.so)                  │
│  ├─ компилирует Luau      │  UNIX-сокет  │  ├─ образ клиента (base)     │
│  ├─ переводит опкоды      ├────────────►│  ├─ хук lua_resume           │
│  └─ читает результат ◄───┼──────────────┤  └─ выполняет Luau в потоке  │
└───────────────────────────┘              │     состояния игры           │
                                          └──────────────────────────────┘
```

## Разделение ответственности

**Агент** (`src/agent/wieen_agent.c`) живёт внутри процесса клиента.

* находит образ клиента в своём адресном пространстве (перебирает
  `/proc/self/maps` и ищет пролог Luau-функций по сигнатуре);
* хукает `lua_resume` — точку, через которую игра запускает любой свой
  скрипт;
* в хуке берёт состояние игры, создаёт поток (`lua_newthread`), грузит в
  него присланный байткод (`luau_load`) и запускает (`lua_resume`);
* отдаёт результат через UNIX-сокет.

**Хост** (`src/cli/wieen.py`, `tools/wieen_compile.cpp`):

* компилирует Luau в байткод своей сборкой Luau (`work/luau-src`);
* переводит номера опкодов в формат клиента (см. ниже);
* пишет байткод в сокет и читает результат.

## Почему сокет, а не почтовый ящик

Внутри клиента запрещены системные вызовы из чужого кода (seccomp), но
рантайм flatpak **не** вырезает `ld.so.preload` — только `LD_PRELOAD` и
`LD_AUDIT`. Значит агент может быть подгружен заранее и спокойно работать
с сокетом: ни один его системный вызов не идёт из кода клиента.

## Хук

`lua_resume` вызывается игрой каждый раз, когда она запускает скрипт.
Агент подменяет её прологин на трамплин (13 байт), который прыгает в
агента и возвращается обратно. Хук прозрачен: аргументы и результат не
меняются, если состояние не похоже на `lua_State` игры.

Исполнять чужой код в хуке безопасно: это тот же поток, что и у игровых
скриптов, и то же состояние — поэтому доступны `game`, `workspace` и всё
остальное.

Состояние игры восстанавливается после запуска: верхушка стека родителя
возвращается на место, а наш поток живёт отдельно.

## Нумерация опкодов

Главная peculiarity клиента: у него **своя** нумерация опкодов Luau, и
даже две.

* **внутренняя** — та, по которой работает интерпретатор: таблица
  диспетчеризации (`0x6a301e0`) содержит 95 живых слотов, разбросанных по
  `0..254`; пустые слоты дают прыжок на адрес `0`;
* **wire** — та, которая записана в байткоде: при загрузке функции клиент
  переписывает каждый опкод через таблицу `0x79219c`, переводя wire-номер
  во внутренний.

Upstream Luau нумерует опкоды `0..94` подряд, поэтому байткод, собранный
нашим компилятором, без перевода выполняется чужими обработчиками (и
падает на пустом слоте).

`tools/opcode_map.py` восстанавливает обе нумерации из образа клиента:

1. внутреннюю — выравниванием обработчиков клиента с обработчиками
   эталонной сборки Luau (Needleman–Wunsch по форме кода, с уточнением по
   профилю вызовов);
2. таблицу «внутренний → upstream», которую клиент держит рядом с
   декодером: она должна совпасть с (1) — и совпадает 95 из 95;
3. wire-нумерацию — как обратную к декодеру.

`tools/wieen_compile.cpp` переводит байткод перед отправкой: номер
опкода каждой инструкции заменяется на wire-номер, а слова, в которых
лежит AUX-значение, обходятся по длине инструкции (длины берутся из
таблицы upstream Luau — они у клиента такие же).

## Что не поддержано

* Скрипты, которые уступают (`wait()`, `task.wait()`), работают: агент
  возобновляет поток сразу же, потому что у игры нет планировщика для
  потока нашего.
* `game.Players.LocalPlayer` требует входа в аккаунт Roblox.
