# Wieen: архитектура

```
хост (宿)                                   клиент Roblox
┌──────────────────────────┐               ┌───────────────────────────────┐
│ wieen CLI                 │               │ agent (.so)                   │
│  ├─ находит pid клиента   │  /proc/pid/mem│  ├─ образ клиента (base)      │
│  ├─ пишет команду ────────┼──────────────►│  ├─ хук интерпретатора Luau    │
│  └─ читает результат ◄───┼───────────────│  └─ выполняет Luau в своём    │
│      (почтовый ящик)      │               │     потоке игрового скрипта   │
└──────────────────────────┘               └───────────────────────────────┘
```

## Разделение ответственности

**Агент** (`src/agent/wieen_agent.c`) живёт внутри процесса клиента.

* находит образ клиента в своём адресном пространстве (перебирает
  `/proc/self/maps`, проверяет пролог Luau-функций по сигнатуре);
* хукает интерпретатор Luau (`luau_execute<false>`) инлайн-детуром;
* в хуке выполняет команды из почтового ящика: `luau_compile` →
  `luau_load` → `lua_pcall` → чтение результата через `lua_tolstring`.

**Хост** (`src/cli/`) — обычная программа с правами root:

* находит процесс клиента по образу в `/proc/*/maps`;
* пишет команду в почтовый ящик (обычная память агента, символ
  `wieen_mbox` — находится через `nm -D` и базу библиотеки);
* ждёт результат (флаги `status`/`seq`).

Почему почтовый ящик, а не сокет: внутри клиента запрещены системные
вызовы из чужого кода (seccomp), а `read`/`write` в память собственного
процесса — обычные обращения к памяти. Хост при этом работает через
`/proc/<pid>/mem` — это обычная запись в память другого процесса, никаких
системных вызовов из клиента не требуется.

## Хук

Детур на точке входа интерпретатора:

```
прыжок → wieen_hook()  →  wieen_tick()  →  трамплин  →  оригинал
```

`wieen_hook()` написан на ассемблере и сохраняет все регистры-аргументы
(интерпретатор их читает уже после возврата), затем вызывает
`wieen_tick()` — она и исполняет команду.

Трамплин собирается в рантайме: первые 16 байт пролога оригинала
копируются в свой буфер, к ним добавляется `mov rax, original+16; jmp rax`,
а в пролог подставляется `mov rax,[rsp]; push rax` — чтобы состояние стека
было точь-в-точь как при обычном `call`.

## Поток выполнения команды

1. хост пишет в `mbox.cmd` исходник, ставит `cmd_len` и свой `seq`;
2. агент, попав в хук (то есть на потоке игрового скрипта), забирает
   команду и исполняет её;
3. агент пишет результат в `mbox.result` и ставит `status = 1`;
4. хост видит `status == 1` и `seq` совпал, читает результат.

Исполнение происходит именно на потоке игрового скрипта — иначе состояние
Luau недоступно и любые вызовы Luau-API из чужого потока небезопасны.
