# Wieen — статус проекта

Дата: 2026-11-19. Ветка: `master`.

Цель: **выполнять Luau-код внутри игры** (Roblox-клиента под Sober) с
доступом к `game`, `workspace` и API игровых скриптов.

**Статус: работает.** Скрипт, скомпилированный на хосте, выполняется внутри
клиента и возвращает результат:

```
$ python3 tools/quick_test.py 'return "wieen-ok"' --raw
connected to the agent
result: wieen-ok
```

## 2. Как это работает

```
хост                          агент (в процессе клиента)        клиент
────                          ─────────────────────────────       ──────
wieen-compile  ──байткод──▶  UNIX-сокет
                              ждёт следующего вызова pre-resume
                              lua_newthread + luau_load
                              lua_resume  ──────────────────────▶  VM клиента
                              читает результат  ◀───────────────
```

1. **Внедрение.** `tools/install_preload.sh` правит `etc/ld.so.preload` в
   рантайме GNOME flatpak. Рантайм вырезает `LD_PRELOAD` и `LD_AUDIT`, но
   `ld.so.preload` доходит до процесса клиента (он грузится собственным
   загрузчиком `libloader.so`, который всё равно пользуется `ld.so`).

2. **Хук.** Агент находит образ клиента в своём адресном пространстве и ищет
   `lua_resume`, `luau_load`, `lua_newthread`, `lua_tolstring` по смещениям с
   проверкой сигнатур. Патчить `lua_resume` нельзя: клиент сверяет байты
   своего кода и уходит через минуту после старта (см. §6). Поэтому хук
   ставится в состояние Luau: агент находит `global_State` и кладёт своего
   обработчика в слот `cb.preresume` — указатель в writable-памяти, который
   VM вызывает перед каждым своим скриптом. Хук срабатывает, когда игра
   запускает любой свой скрипт, — это и есть безопасное место для
   исполнения чужого кода: тот же поток, то же состояние.

3. **Исполнение.** Агент создаёт поток (`lua_newthread`), грузит в него
   байткод (`luau_load`) и запускает (`lua_resume`) — с состоянием игры
   общий, поэтому доступны `game`, `workspace` и всё остальное.

4. **Уступание.** Скрипт, который вызывает `wait()`, останавливается на
   `LUA_YIELD`. У игры нет планировщика для нашего потока, поэтому агент
   возобновляет его сразу же и доводит скрипт до конца.

5. **Нумерация опкодов.** Главная сложность: клиент нумерует опкоды Luau
   иначе, чем upstream (см. §4). Скомпилированный на хосте байткод
   переводится в формат клиента перед отправкой.

## 4. Главная находка: у клиента своя нумерация опкодов

Клиент — это Luau с **переставленными номерами опкодов**:

* таблица диспетчеризации клиента (`0x6a301e0`) содержит 95 живых слотов,
  разбросанных по `0..254`, тогда как upstream нумерует опкоды `0..94`
  подряд; пустые слоты дают прыжок на адрес `0` — это и был «RIP=0»;
* байткод, который читает клиент, использует **третью** нумерацию («wire»):
  при загрузке функции клиент переписывает каждый опкод через таблицу
  `0x79219c`, переводя wire-номер в его внутренний.

Восстановлено три таблицы:

| что | где | как |
|---|---|---|
| внутренняя нумерация клиента | таблица диспетчеризации `0x6a301e0` | выравнивание обработчиков клиента с эталонной сборкой Luau (`tools/opcode_map.py`) |
| таблица «внутренний → upstream» | `0x79229c` | найдена в `.rodata`, рядом с декодером |
| wire-нумерация | обратная к декодеру `0x79219c` | та же |

Проверка: собственная таблица клиента (`internal → upstream`) совпала с
нашим выравниванием **95 из 95** — значит спорные пары (13 «слабых»
вхождений) тоже верны.

Итог: wire-номер опкода `u` равен `(-29 * u) mod 256`, а внутренний
номер клиента берётся из его таблицы. `tools/opcode_map.py` пересобирает
`tools/opcode_map.h`, `tools/wieen_compile.cpp` переводит байткод перед
отправкой (AUX-слова при этом не трогаются — длина инструкции берётся из
той же таблицы upstream).

## 6. Клиент проверяет байты своего кода

Хук на `lua_resume` пришлось убрать: клиент примерно через 65 секунд после
старта сверяет свой text с эталоном и уходит, если байты не совпали.

* Запись тех же байт обратно (режим `WIEEN_TOUCHTEXT`) — клиент жив: дело
  не в грязной странице, а в содержимом.
* Перекодировка `mov rbp,rsp` в эквивалентную (`48 8b ec` вместо `48 89 e5`)
  — клиент уходит: проверяются байты, а не смысл инструкции.
* То же самое с прологом `luau_load`, который хуком не трогался, — тоже
  уходит: проверяется весь text, а не только изменённая функция.
* `perf_event_open` с аппаратным breakpoint'ом работает и в песочнице
  (`bp_len=8`, `perf_event_paranoid=2`), но `perf_event_attr.sigtrap` на
  ядре `7.3.1-1-cachyos` отклоняется с `EINVAL` — синхронного `SIGTRAP` не
  получить.

Значит, хук должен обходиться без изменения кода. В Luau для этого есть
готовый слот: `global_State` лежит в куче, а поле `cb.preresume` — это
указатель, который VM вызывает перед каждым своим скриптом. Подмена этого
указателя меняет только writable-память, которую проверка текста не видит.

### Как агент находит состояние

1. В образе клиента есть функция `base+0x22e260b` — это callback
   `cb.userthread`, который Roblox кладёт в каждое состояние. Её адрес
   служит якорем: агент сканирует резидентные страницы (через `mincore`;
   арена mimalloc — гигабайт, но живых страниц мало) и ищет место, где по
   смещению `+0x6a0` лежит именно этот указатель.
2. Проверка кандидата: по `+0x6a0` — указатель в text клиента, по `+0x678`
   и `+0x650` — хуки Luau (или нули), по `+0x6b0` — маленький счётчик, и
   рядом должен быть живой `lua_State`, у которого `+0x38` указывает на это
   же состояние.
3. Кандидатов оказалось два: у клиента два Luau-VM. Тот, что не
   возобновляет скрипты, отпадает сам собой; тот, что возобновляет, и есть
   VM игры. Чтобы не гадать, агент спрашивает у VM пробу
   (`tools/probe.luau`): `typeof(game) .. "/" .. typeof(workspace)`.
   У VM игры ответ `Instance/Instance`, у чужой — `nil/nil`.
4. Проба — обычный Luau-скрипт, а клиент грузит только байткод, поэтому
   проба компилируется на хосте при сборке агента: `tools/bin2h.py` кладёт
   байткод в `build/probe_bytecode.h`.

### Байткод больше 280 байт не грузится

> Лимит снят контейнером версии 1 — см. §17. Раздел оставлен как история
> первого этапа.

`luau_load` у клиента — это не голый Luau, а обёртка Roblox: она умеет
грузить и «доверенный» байткод (с подписью сервера), и обычный, но только
если он **меньше 280 байт**. Всё, что больше, получает отказ
`wieen: bytecode corrupted`.

Проверено точно: блоб 277 байт грузится, 280 — уже нет. Порог не зависит
ни от числа строк, ни от числа констант: это размер всего блоба.

На самом деле 280 — это граница между двумя путями загрузчика: меньше
`0x118` — голый байткод, не меньше — контейнер с подписью (см. §17).
Поэтому порог не «отказ», а переключатель формата.

Голый `luau_load` из другой копии Luau внутри клиента не помогает: копии
разных версий, и состояние у них разное — клиент падает или поток
получается мёртвым (`WIEEN_ALTLOAD=<смещение>` выбирает загрузчик руками,
см. `src/agent/luau_symbols.h`).

Помогает разбиение скрипта на части (исторически — чтобы часть влезала в
279 байт; после §17 части идут в контейнере, но механизм остался):

* хост компилирует каждую часть отдельно;
* локальные переменные верхнего уровня становятся глобальными, поэтому
  части по-прежнему делят состояние (`tools/wieen_compile.cpp`, функция
  `split_script`);
* части кладутся в сокет кадром `WIEENMUL` + число частей + длины и байты
  частей, агент выполняет их подряд в той же VM (`run_pending`);
* если часть не влезает даже без информации о строках, скрипт не грузится
  вовсе — тогда запись `local function` с телом побольше надо писать
  компактнее.

Проверено: скрипт в 1170 байт байткода (5 частей) выполняется, состояние
между частями общее (`30/60/90/150` для арифметики в трёх частях).

### Права потока

У каждого потока Roblox есть набор прав (capabilities): поток без них не
имеет права трогать инстансы, и песочница отвечает «lacking capability
Basic». Поток, который делает агент, прав не получает вовсе — `game` и
`workspace` читаются, а `workspace.CurrentCamera` нет.

Маска прав лежит в состоянии потока по смещению `+0x0c` (`u32`): у потока
игры там `0x1` (у другого потока игры встречается `0x5`), у нашего — `0`.
Агент копирует маску родителя в свой поток сразу после `lua_newthread`, и
доступ к игровым объектам появляется:

```
return typeof(workspace.CurrentCamera)   -- Instance
return tostring(workspace.CurrentCamera.CFrame)  -- -291.23, 303.57, -739.52, ...
```

Права `CreateInstances` (создание инстансов, `Instance.new`) в наборе
родителя нет, и найти их не удалось: у состояний VM маски разные и не
вложены друг в друга, а объединение всех масок даёт мусор. Поэтому
`Instance.new` из агента по-прежнему отклоняется песочницей, и вместе с
ним `GetService` для всех служб, кроме `Workspace`: у потока агента нет
контекста скрипта игры.

> Раздел описывает первый этап и оставлен как история. Права скрипта
> нашлись позже и живут в окружении чанка, а не в маске потока — см. §12.

### Почему print не попадает в консоль F9

`print` идёт в игровой канал `FLog::CreatorOutput` — ровно тем же, что и
print скриптов игры, — и потому виден в логе клиента и в консоли Sober.
Консоль F9 внутри игры смотрит на сообщения *контекста скрипта*: у потока
агента (простой协процессы, созданной `lua_newthread`) такого контекста нет.

### loadstring в клиенте отключён

Глобальная `loadstring` есть, но клиент отвечает «loadstring() is not
available» — это проверка движка Roblox, а не права потока: с полным
набором прав (`0x7fff`, объединение масок всех состояний VM) отказ тот
же. Проверка идёт по цепочке контекстов скрипта (`+0x60` у узла, флаг
контекста `+0x8f4`), а у потока агента этой цепочки нет.

В клиенте есть и флаг `LoadStringEnabled` (регистрируется в 0x1c7f600, его
значение живёт в хранилище флагов Roblox) — его можно было бы переключить,
но проверка `loadstring` идёт не по флагу, а по контексту.

Точнее: рабочий путь у `loadstring` в клиенте есть (он компилирует исходник
внутри себя, 0x4312794), но закрыт двумя проверками: бит «RobloxScript
context» и флаг контекста `+0x86d`. У потока агента контекста скрипта нет,
поэтому оба отказа.

### Свой loadstring

Раз компиляция в клиенте закрыта контекстом, а исходник известен только в
момент вызова, loadstring сделан через хост:

1. хост подставляет в скрипт заготовку — `local loadstring = function(src)
   return coroutine.yield(src) end` (локальная переменка, чтобы глобальная
   `loadstring` игры не пострадала);
2. скрипт вызывает `loadstring(src)` — поток игры замирает на `yield`;
3. агент видит, что отдали строку, и просит хост скомпилировать её (кадр
   `\x00compile:` по тому же сокету);
4. хост компилирует (с переводом опкодов) и отдаёт байткод (кадр
   `\x00compiled:`);
5. агент грузит байткод в тот же поток — функция оказывается на стеке, и
   `yield` возвращает её; скрипт идёт дальше.

Если вместо исходника пришла ссылка (`http://` или `https://`), шаг 3
отправляет хосту кадр `\x00fetch:` — хост скачивает текст и компилирует его
так же, как обычный исходник. Свой HTTP-клиент клиенту не нужен:
`game:HttpGet` в нём отсутствует.

Поэтому `game:HttpGet(url)` и `game:HttpGetAsync(url)` компилятор заменяет
на `_WH(url)` — она отдаёт хосту кадр `\x00http:`, а хост возвращает чанк,
который возвращает скачанный текст (кадр `\x00compiled:` с обычным
байткодом). Частый вид `loadstring(game:HttpGet(url))` заменяется плотнее:
в `loadstring(url)`, и текст вообще не проходит через клиент. Ошибка
скачивания возвращается в скрипт как `error(...)`, а не как `nil`.

Длинный исходник режется на части и приходит кадром `WIEENLSP`: диспетчер
принимает функции частей и возвращает одну функцию над ними. Каждая часть
получает свою заготовку `loadstring`, поэтому скачанный скрипт может
загрузить следующий — в том числе по ссылке.

Проверено: `loadstring("return 6*7")()` → `42`, loadstring с циклом и с
`print` — работает, `print` виден в логе клиента; ссылка на локальный
сервер, большой исходник по ссылке (`3240`) и вложенный loadstring — тоже.
Размер одного чанка теперь ограничен не 280 байтами, а 4 МиБ — лимит
снят контейнером версии 1 (см. §17); длиннее — по-прежнему разбиение.

Что пробовали:
- скопировать маску прав потока (поле `+0x0c`) — доступ к игровым объектам
  появился, но службы и консоль остались закрыты;
- скопировать поля потока (`+0x10`, `+0x18`, `+0x20`, `+0x28`, `+0x30`) — либо
  ничего не меняется, либо поток перестаёт просыпаться;
- выполнить скрипт в самом потоке игры (`WIEEN_INTHREAD=1`): нужен
  `lua_pcall` той же копии Luau, а копии в клиенте разных версий — вызов
  чужой копии убивает клиент.

### Гонка при поиске состояния

Поиск состояния VM читает память клиента, а игра её в это время освобождает:
страница может исчезнуть между моментом, когда её увидели, и моментом, когда
её прочитали. Клиент на этом падает.

Обработчики сигналов теперь ставятся всегда, но чужой сигнал отдаётся
обработчику игры без изменений — как и раньше. Ловушку ловит только поиск
состояния: он запоминает, на каком потоке работает, и при своей ошибке
делает `siglongjmp` — поиск начинается заново (`g_scan_jmp`).

### Что это дало

* Клиент жив: 120 секунд без единого изменённого байта, `sendto=0`,
  `fatal=0`.
* Скрипты выполняются в VM игры: `tools/selftest.py` — 35/35,
  `tools/soak.py` — 6/6, а `print()` из скрипта виден в логе клиента.

## 7. Почему игра падала (и что с этим сделано)

Первая версия агента ставила свои обработчики `SIGSEGV`/`SIGBUS`/`SIGILL`/
`SIGFPE` **поверх** обработчиков игры и на любой сигнал завершала процесс.
Клиент же поднимает `SIGSEGV` сам — в отчёте видно `si_code = 0` (`SI_USER`,
отправитель — собственный pid), это его краш-репортер. Агент превращал
такой сигнал в смерть процесса и писал в лог `signal 11`.

Что изменено:

- **Обработчики сигналов ставятся только по `WIEEN_FAULTLOG=1`** и первым
  делом передают сигнал обработчику игры; журнал пишется только если
  обработчика не было вовсе.
- **Горячий путь хука ничего не читает**: раньше при промахе карты памяти он
  раз в четыре вызова открывал `/proc/self/maps`. Теперь, если скрипт не
  ждёт, хук — это счётчик и одна проверка флага.
- **Код клиента не трогается вообще**: патч `lua_resume` клиент проверяет и
  из-за него уходит (см. §6), поэтому обработчик живёт в состоянии Luau.
- **`lua_resume(thread, parent, 0)`**: глубина C-стека берётся у состояния
  игры, поэтому глубоко рекурсивный скрипт не выйдет за стек процесса.
- **Протокол**: слишком большое сообщение вычитывается и получает ответ
  (раньше обрезалось и рассинхронизировало сокет); по таймауту ожидающий
  скрипт сбрасывается, а не выполняется позже «за спиной» следующей команды.
- Пути сокета и лога строятся из `$HOME`; `env_flag()` считает пустое
  значение переменной её отсутствием (`flatpak override --unset-env`
  оставляет в профиле пустые строки).

## 8. Что было с клиентом на этой машине

Клиент иногда приходит *новым* сбором (хеш образа `9a5bd2d0cf53d9ff` вместо
известного `18d8af04a276288d`): тогда подписи функций не совпадают и агент
не находит `lua_resume`. Лечится пересборкой таблиц под текущий APK
(`make symbols`) и новыми подписями. Иногда клиент не дотягивается до CDN и
уходит с «Couldn't reach Roblox» — это сеть, а не агент.

`Wrap-deformer fetching meshes resulted in error`, `sendto failed ...
Address family not supported by protocol`, `Asset (Image) ...` и внезапное
`lifecycle: clean_exit_success` через пару секунд после старта — это сам
клиент: у него не работает сеть до CDN (`tr.rbxcdn.com` не резолвится).
Агент тут ни при чём: то же самое происходит с `WIEEN_OFF=1`.

Отдельная ловушка: `flatpak override --user --env=...`, а потом
`--unset-env`, оставляет в профиле переменные с пустым значением, и клиент
после этого закрывается на старте. Проверять `flatpak override --user --show
org.vinegarhq.Sober`, чистить `flatpak override --user --reset`, а
одноразовые флаги передавать так: `flatpak run --env=WIEEN_FAULTLOG=1
org.vinegarhq.Sober`.

## 9. После `flatpak update` агент молча перестаёт загружаться

flatpak обновляет рантайм не на месте: он ставит новый деплой и
переключает симлинк `active`. Наш `etc/ld.so.preload` остаётся в старом
деплое и исчезает вместе с ним. Признаки: в `agent.log` нет новой сессии
`=== wieen agent (pid N) ===`, `exec` говорит `no agent listening`, а файл
`wieen.sock` лежит от прошлой сессии и он мёртвый.

- `wieen status` / `wieen exec` теперь читают preload активного деплоя и
  прямо пишут, что его нет, и какой командой вернуть;
- `wieen launch` сам зовёт `sudo tools/install_preload.sh`, если preload
  пропал, и только потом стартует Sober;
- `tools/install_preload.sh` берёт ref рантайма из
  `flatpak list --app --columns=application,runtime` (не парсит локализованный
  `flatpak info`) и проверяет, что запись легла.

Заодно: клиент собран с `p_align 0x4000` (16 KiB страницы), поэтому ELF
заголовок живёт на `r--p` странице, а `r-xp` начинается с `base+0x4000`.
Агент больше не ищет «один исполняемый диапазон, содержащий базу» — он
собирает все исполняемые маппинги образа и ищет подписи во всех. Каждый
ранний выход теперь пишет причину в лог, а `WIEEN_SCAN=1` печатает всех
кандидатов с расстоянием до старого офсета (этим таблица и пере-выводится).

## 11. Рубеж 1: исполнение в потоке игры (`WIEEN_INTHREAD=1`)

Хук `preresume` получает `lua_State` игры в тот момент, когда клиент его
возобновляет. Значит, скрипт можно вызвать прямо в этом потоке: он бежит с
тем же состоянием, что и код игры, а не в отдельном потоке агента.

Что для этого восстановлено:

* `lua_pcall` в этой сборке **отсутствует как функция**: `lapi.cpp`
  вкомпилирован, в образе остались только `luaD_pcall` (`0x22e5729`) и
  `luaD_call` (`0x22e5b93`), а единственные два вызова `luaD_pcall` — это
  yieldable-обёртка (`0x31f868f`) и сам интерпретатор. Прежние четыре
  кандидата (`0x22e836e`, `0x22e8456`, `0x22e854e`, `0x22e8696`) — не
  `lua_pcall`, поэтому и роняли клиент.
* `lua_pcall` собран заново по upstream: `luaD_pcall(L, f_call, &c,
  savestack(c.func), 0)`, где `f_call` зовёт `luaD_call`. Аргументы и
  возвращаемое значение совпадают с `lua_pcall` из `lapi.cpp`.
* `preresume` вызывается, когда поток ещё `LUA_YIELD`. `luau_execute` в
  таком состоянии сразу выходит и стек не меняется (проверено), поэтому на
  время вызова статус ставится `LUA_OK`, а после — возвращается прежний.
* До и после вызова снимается состояние (`WIEEN_STATELOG=1`): `status`,
  `active`, `nCcalls`, `baseCcalls`, `ci`, `baseci`, `base`, `top`. На
  удачных и на ошибочных вызовах они совпадают — игра не замечает, что мы
  здесь были.
* Скрипт, который уступает (`wait()`, `task.wait()`), продолжать из этого
  вызова нельзя: `lua_yield` отказывает — «attempt to yield across
  metamethod/C-call boundary» (у клиента текст «thread is not yieldable»).
  Агент узнаёт этот отказ по тексту ошибки, возвращает стек и
  **перезапускает скрипт обычным путём** — в своём потоке с циклом
  возобновления. Поэтому `selftest.py` даёт 35/35 и с `WIEEN_INTHREAD=1`,
  и без него.

Что это дало:

* `print` из скрипта попадает в канал клиента `FLog::CreatorOutput` — тот
  же, куда пишут скрипты игры (см. §6, «Почему print не попадает в консоль
  F9»).
* `game`, `workspace`, `GetService` работают так же, как в потоке агента.

Чего это не дало: **прав скрипта**. У потока игры в момент хука маска прав
`0x1`, и `Instance.new` по-прежнему отвечает «lacking capability
CreateInstances», а `workspace.CurrentCamera` — «lacking capability Basic».
Права нашлись в другом месте — см. §12.

### Маска `+0x0c` — не то, что проверяет песочница

Гипотеза «права можно одолжить: подменить маску в `lua_State +0x0c` на
время вызова» проверена и **не подтвердилась**. Маски `0x1`, `0x3`, `0x5`,
`0x1b`, `0x78`, `0x7f`, `0xff`, `0x1ff`, `0xffff`, `0xffffffff`
(`WIEEN_GAMECAPS`, `WIEEN_CAPSFILE`) не меняют ответа: `Instance.new("Part")`
всё так же отклоняется. Значит, песочница спрашивает права не в этой маске,
а в цепочке контекста скрипта (той же, что закрывает `loadstring`, §6).
Маска возвращается на место после каждого вызова, клиент жив.

Второй опыт — выбрать поток по маске (`WIEEN_WANTCAPS`/`WIEEN_WANTFILE`:
потоки с неподходящей маской пропускаются, скрипт ждёт следующий). Маски
`0x1`, `0x5`, `0xa` скрипт получают, но `Instance.new` в них так же
отклоняется; потоки с `0x1b` и `0x78` за время ожидания (10 с) не
возобновляются вовсе. Значит, `CreateInstances` нет ни у одной из масок,
которые игра выдаёт своим потокам, — право приходит от контекста скрипта,
а не от маски потока.

### Надёжность канала

`read`/`write` агента повторяются при `EINTR`: сигнал игры больше не рвёт
соединение. Именно это давало «broken pipe» в `soak.py` — один потерянный
ответ на несколько скриптов, а `soak.py` принимал такой ответ за успех.

## 12. Рубеж 2: права скрипта (`WIEEN_ENVCAPS`)

Права на инстансы игра спрашивает **не** в маске потока (та закрывает
только `Instance.new`, и то не всегда). Проверка идёт по маске, которая
лежит в окружении замыкания — то есть у самого чанка, который мы
загрузили.

### Где лежит маска

```
closure = *(TValue*)(top - 16)      // то, что мы только что положили в стек
env     = *(void**)(closure + 0x18) // Closure + 0x18 = env (luau lobject.h)
mask    = *(u64*)(env + 0x70)       // указатель на 64-битную маску
```

`Mask` — именно указатель: клиент хранит маски централизованно (одна на
набор прав), поэтому подменять надо указатель, а не значение. Агент так и
делает: кладёт в `env + 0x70` адрес своей маски `g_env_mask`, зовёт
`luaD_pcall`, затем возвращает прежний указатель. Данные клиента не
меняются ни на байт.

Второй путь той же проверки — синглтон-checker
`base + 0x6f85d50` (через `0x2992ee0`), у него `+0x30` — разрешённая
маска, `+0x38` — ленивый колбэк. Подмена `+0x30`
(`WIEEN_CHECKERCAPS`) при **одноразовой** подмене ничего не меняет: за
время вызова клиент переписывает кэш своей маской. Почему и как это
исправлено — §13.

### Набор прав (64 бита)

Таблица имён — `capabilityName()` по RVA `0x31b4d18`. Ключевые биты:

| бит | маска | имя |
|-----|-------|-----|
| 0 | `0x1` | `Plugin` |
| 1 | `0x2` | `LocalUser` |
| 3 | `0x8` | `RobloxScript` |
| 8 | `0x100` | `RunClientScript` |
| 9 | `0x200` | `RunServerScript` |
| 17 | `0x20000` | `LoadString` |
| 18 | `0x40000` | `ScriptGlobals` |
| 19 | `0x80000` | `CreateInstances` |
| 20 | `0x100000` | `Basic` |
| 34 | `0x400000000` | `Players` |

Полный перечень битов 0-5, 8, 9, 11, 15, 16-31, 32-53 и 60-62 снят с
клиента; `0xffffffffffffffff` покрывает всё.

У потока игры в момент хука `[[L+0x20]+0x80] = 0x303fffffffffff0b`
(биты 0,1,3, 8-15, 16-47, 48-53, 58,59) — то есть почти всё, кроме
`CreateInstances` и `Players`. Эта маска — маска **потока**, и её подмена
(`WIEEN_THREADCAPS`) по-прежнему не открывает свойства на игровых
инстансах.

### Что открылось

`WIEEN_INTHREAD=1` (права одалживаются по умолчанию, полный набор):

```
local h = workspace:GetDescendants()[38]
h.WalkSpeed = 100          -- ok
return h.WalkSpeed         -- 100
```

* `Instance.new("Part")`, `f.Parent = workspace`, `f.Transparency = 0.5` —
  работают; `Transparency` читается обратно `0.5`.
* Запись свойств на игровых инстансах **проходит и держится**:
  `Humanoid.WalkSpeed` читается `100` в следующем соединении. Раньше
  запись молча терялась.
* `Size` у непривязанного `Part` по-прежнему читается как `4, 1.2, 2`:
  это не песочница, а то, что запись `Size` применяется отложенно (part
  пересчитывает размер при входе в мир).

### Что всё ещё закрыто

Чтение свойств, которые клиент отдаёт только «своим»:

```
game.Players.LocalPlayer            -- lacking capability Players
workspace.CurrentCamera             -- lacking capability Camera (Basic)
```

Оба ответа одинаковы и при `ENVCAPS`, и при `ENVCAPS` + `THREADCAPS`.
Причина оказалась не в отдельной проверке, а в гонке за общий checker —
см. §13: со сторожем `game.Players.LocalPlayer.Character` читается. Для задачи «поднять WalkSpeed» это не
мешает: `Humanoid` находится обходом `workspace:GetDescendants()`.

### Стабильность

`selftest.py` — 35/35, `soak.py` — 6/6 (включая 180 с простоя),
`stress.py` — 116 скриптов, клиент жив; всё с одним `WIEEN_INTHREAD=1`.
В логе агента нет ни одного падения. Маски потока и checker'а
возвращаются на место после каждого вызова, даже если скрипт упал с
ошибкой; маски окружения и маска по умолчанию остаются одолженными —
иначе не работают колбэки, см. §17.

### Флаги

| флаг | что делает |
|------|------------|
| `WIEEN_ENVCAPS=<маска>` | какую маску одолжить окружению чанка (по умолчанию `0xffffffffffffffff`; `0` — выключить) |
| `WIEEN_THREADCAPS=<маска>`, `WIEEN_THREADCAPSFILE=<файл>` | подменить `[[L+0x20]+0x80]` |
| `WIEEN_SANDBOXAT=<смещение>` | другое смещение маски в окружении (по умолчанию `0x80`) |
| `WIEEN_SANDBOXLOG=1` | печатать `[[L+0x20]+0x80]` и маску окружения |
| `WIEEN_ENVLOG=1` | печатать `closure`, `env` и указатель маски чанка |
| `WIEEN_CHECKERLOG=1` | дамп синглтона-checker (`+0x00..+0x78`) |
| `WIEEN_CHECKERCAPS=<маска>` | подменить `checker + 0x30` (проверено: не влияет) |
| `WIEEN_FRAMELOG=1` | кадры стека в момент хука |
| `WIEEN_DUMPSTATE=1` | полный дамп полей состояния потока |

## 13. Рубеж 2, продолжение: checker и его гонка

§12 заканчивался выводом «подмена `checker + 0x30` ничего не меняет».
Это верно только для **одноразовой** подмены. Причина — гонка.

### Как устроена проверка записи свойства

Путь записи — `0x2300ea8`. Он берёт из дескриптора класса две маски
(`+0x38` и `+0x90`), строку операции `"write"` и имя свойства и зовёт
общий checker `0x2158c2c(checker, required, op, name)`.

Сам checker — общий на весь клиент синглтон `base + 0x6f85d50`
(достаётся через `0x2992ee0`):

| поле | что лежит |
|------|-----------|
| `+0x20` | `lua_State`, для которого маска считается |
| `+0x30` | разрешённая маска (кэш) |
| `+0x38` | ленивый колбэк `base + 0x42d4331` |

Колбэк считает:

```
allowed = (required | ~0xff)
        & [[state + 0x20] + 0x80]     // маска контекста потока
        & *[env(state) + 0x70]        // маска окружения чанка
```

`0x2158c2c` сначала вызывает колбэк (если он есть), кладёт результат в
`+0x30`, **обнуляет `+0x38`** и только потом сравнивает
`missing = required & ~allowed`. При отказе сообщение собирает
`0x31b50ec` (`"The current thread cannot {} '{}' ({} {})"`), а имя
недостающей способности даёт `capabilityName()` (`0x31b4d18`).

### Почему одна подмена не помогала

Синглтон общий: его `+0x30`/`+0x38` переписывает **любой** скрипт игры,
который в этот момент что-то читает или пишет. Мы одалживали маску один
раз перед `luaD_pcall`, а за время вызова клиент успевал положить туда
свою, меньшую. Отсюда «то проходит, то нет» и ложный вывод §12.

Отдельно: диагностика `WIEEN_MASKLOG` звала аксессор `0x22ea488`,
который сам пишет `+0x30` и обнуляет `+0x38`, — то есть портила кэш
перед каждым вызовом. Поэтому все прогоны с ней отказывали. Диагностика
удалена.

### Решение: сторож

Перед вызовом агент поднимает маленький поток, который на всё время
`luaD_pcall` держит:

* `checker + 0x30 = 0xffffffffffffffff`
* `checker + 0x38 = 0`

После вызова оба поля возвращаются к прежним значениям. Данные клиента
не меняются ни на байт, код не патчится. `WIEEN_GUARD=0` выключает
сторожа.

### Что это дало

На чистом `WIEEN_INTHREAD=1` (без других флагов), живое переживание
`Ugc`, place 134720269349402:

```lua
local h = game.Players.LocalPlayer.Character:FindFirstChildOfClass("Humanoid")
h.WalkSpeed = 0        -- 0, 16, 50, 0, 24, 30, 0 — семь из семи
```

* `Instance.new("Part")`, `Parent`, `Name`, `Anchored`, `Transparency`,
  `Humanoid.JumpPower` — проходят и держатся.
* `game.Players.LocalPlayer.Character` читается (в §12 это ещё
  отказывало: гонка та же).
* Запись `WalkSpeed` теперь не «иногда», а стабильно: серия из семи
  значений подряд, без пропусков.

### Почему сторож иногда молча не включался

`refresh_maps()` читал `/proc/self/maps` в таблицу на 1024 записи. У
живого клиента с NVIDIA и десятком библиотек этих записей 7–10 тысяч,
поэтому всё выше первой тысячи — стеки потоков, checker, куча — считалось
«не отображённым». `is_mapped(checker + 0x38)` возвращал ложь, ветка
заёма пропускалась, и в логе не появлялось ни `the caps of the checker
are lent`, ни `the guard holds the checker`. Скрипт при этом исполнялся,
но проверки прав шли по чужой, меньшей маске — отсюда `lacking
capability Players` и `UI`.

Таблица увеличена до 16384 записей, а перед заёмом checker'а карта
обновляется явно: адрес checker'а у каждого потока свой (он лежит в
стеке потока), и снимок карты должен быть свежим.

Второй аргумент `0x2992ee0` — `1`, как в самом клиенте (`0x2051edc`).
С `0` аксессор выбирает другое TLS-поле и может вернуть адрес из стека
вызывающего потока: `+0x30` там похож на маску, но это не checker, и
сторож охраняет не то.

Наконец, `watcher_thread` при переходе в VM переживания теперь ставит
`g_toast_state = 1`: раньше приветствие не запускалось вовсе, если
клиент стартовал в меню и игрок заходил в место позже.

### Регрессия

`selftest.py` — 35/35, `soak.py` — 6/6 (180 с простоя),
`stress.py` — 116 скриптов, клиент жив. Всё с одним `WIEEN_INTHREAD=1`.

### Флаги

| флаг | что делает |
|------|------------|
| `WIEEN_GUARD=0` | выключить сторожа checker'а |
| `WIEEN_CHECKERCAPS=<маска>` | какую маску класть в `checker + 0x30` (по умолчанию полная) |
| `WIEEN_ENVCAPS=<маска>` | маска окружения чанка; `0` выключает |
| `WIEEN_ENVKEEP=0` | возвращать маски окружения после вызова (по умолчанию остаются, см. §17) |
| `WIEEN_DEFKEEP=0` | возвращать маску по умолчанию `0x703eb90` (по умолчанию остаётся) |

## 14. Приветствие при входе в переживание

Когда агент выбирает VM переживания (`game.Name` не `LuaApp`), он сам
показывает, что он в игре. Скрипт приветствия лежит в `tools/toast.luau`,
компилируется в `build/toast_bytecode.h` и вшивается в агента, как и проба.

Два канала, оба штатные для клиента:

```lua
local LOGO = "rbxassetid://113328400853000"

local sg = game:GetService("StarterGui")
local opt = {}
opt.Title = "pwned by Wieen"
opt.Text = "t.me/WieenExploit"
opt.Duration = 10
opt.Icon = LOGO
sg:SetCore("SendNotification", opt)
print("pwned by wieen! t.me/WieenExploit")
```

* `SetCore("SendNotification")` рисует уведомление в углу экрана; клиент
  сам его убирает через `Duration`.
* `print` попадает в консоль F9 как `FLog::CreatorOutput`
  (в `sober_logs/latest.log` это видно строкой
  `Info [FLog::CreatorOutput] pwned by wieen! ...`).
* `Icon` — это `rbxassetid`, а не путь в файловой системе: картинку
  клиент берёт только из CDN Roblox. Логотип `docs/logo.png` (928×928)
  один раз залит в аккаунт как Image `113328400853000` (модерация
  пройдена, `thumbnails.roblox.com` отдаёт `Completed`), и его id стоит
  в `LOGO`. Если строку `LOGO` сделать пустой, уведомление уйдёт без
  картинки, но с заголовком и текстом.

Свой ScreenGui больше не нужен и из скрипта удалён: уведомление рисует
сам клиент.

Как это устроено в агенте:

* `g_toast_state = 1` ставится в момент выбора VM переживания;
* на ближайшем `preresume`, когда нет команды сокета, вызывается
  `run_toast`: он подкладывает байткод приветствия в `g_pending` и зовёт
  `run_pending` — то есть скрипт идёт тем же путём, что и команда
  пользователя, с заёмом прав и сторожем checker'а;
* `g_force_inthread` включает исполнение в потоке игры на время тоста,
  даже если `WIEEN_INTHREAD` не задан: без потока игры прав на
  `StarterGui` нет;
* пока место не поднялось, скрипт возвращает `"wait-player"` (нет
  `LocalPlayer`) или `"wait-gui"` (нет `PlayerGui`), а если ядро ещё не
  зарегистрировало `SendNotification` — просто `"wait"`. Агент повторяет
  попытку раз в секунду, до десяти минут: место грузится дольше, чем
  кажется, а счётчик `preresume` не годится — они бьются тысячами в
  секунду, и сотня попыток кончается раньше, чем появится игрок.
  Ошибка `SetCore` (ядро ещё не зарегистрировало метод) тоже даёт
  `"wait"`, так что `print` не дублируется в F9.

Проверено на живом клиенте (place 134720269349402): в логе агента
`wieen: the greeting, try 1: ok`, в логе клиента — строка `pwned by
wieen! t.me/WieenExploit`. Уведомление видно в правом нижнем углу
вместе с логотипом; `ATTACH` в GUI показывает `ATTACHED Ugc` только
после точного `ok` от `tools/toast.luau`.

Первый загруженный логотип (`96134879839401`) остался приватным:
`thumbnails.roblox.com` отдавал для него `/PrivateImage/`, и клиент не
рисовал его ни в уведомлении, ни в обычном `ImageLabel`. Новый ассет
`113328400853000` отдаётся как `/Image/` и виден.

## 15. Образ клиента появляется позже, чем кажется

Агент ищет образ клиента в своём процессе и ждёт его ограниченное время.
Сначала это была минута — и один запуск показал, почему этого мало:

```
info: app: lifecycle: fs_init delta=61348.02886799723ms
```

Sober поднимает файловую систему клиента **61 секунду**, и только после
этого `libroblox.so` попадает в процесс. Минута ожидания кончалась за
секунду до этого, агент писал `no client image in this process, nothing to
do` — и в игре не было ни уведомления, ни сокета.

Теперь ожидание — десять минут, с отметкой в логе раз в минуту:

```
wieen: no client image yet, 60 s
```

Вторая ловушка того же места: `find_client_base` берёт самый большой
исполняемый ELF-образ, а в процессе их может быть несколько. Если в
выбранном образе нет ни одной сигнатуры Luau (в логе это
`has no Luau in it`), агент больше не сдаётся: он запоминает этот образ в
`g_reject` и ищет дальше, до четырёх отводов и двадцати кругов с паузой в
секунду. Раньше один неверный выбор навсегда выключал агента в процессе.

В логе теперь виден и путь образа:

```
wieen: image of the client at 0x7f8e1d11b000, hash 18d8af04a276288d (/home/.../libroblox.so)
```

Проверка: запуск, где `fs_init` занял 61 с, доводит агента до
`listening on .../wieen.sock` и до приветствия в игре.

## 16. Интерфейс

`src/gui/wieen_gui.py` — PyQt6, один файл. Чёрное окно с мягким фоном
(градиент и два размытых пятна), панели — стеклянные карточки. Слева две
кнопки: `MOMENTUM RUN` и `ATTACH`, справа рабочая область из двух вкладок.

```
MOMENTUM RUN  диалог, в котором сами идут шаги:
              01 BUILD    make agent compile
              02 INSTALL  sudo -n ... || pkexec env SUDO_HOME="$HOME" ...
              03 LAUNCH   python3 src/cli/wieen.py launch
              конец: «зайди в плейс, затем нажми ATTACH»
ATTACH        Agent().exec("return tostring(game.Name)")
              Agent().exec(содержимое tools/toast.luau)   (повтор, пока "wait*")

SCRIPT   редактор Luau с подсветкой, номерами строк, RUN / OPEN / SAVE / CLEAR
         консоль находится прямо под редактором, вывод игры и ошибки красным
AGENT    сокет, preload, агент, место, размер сборки
```

* поля `place url` нет: Sober всегда стартует без аргументов, место выбирает
  сам пользователь, а attach проверяет `game.Name` и не даёт соврать — если
  клиент в меню, он отвечает `LuaApp` и attach говорит об этом;
* диалог `MomentumDialog` держит свои `QProcess` и живёт дольше шагов: после
  закрытия окна сам Sober остаётся процессом главного окна, его лог идёт в
  CONSOLE;
* установка не требует терминала: `sudo -n`, а если тикет холодный —
  `pkexec env SUDO_HOME="$HOME" bash tools/install_preload.sh`, потому что
  `SUDO_USER` под polkit не выставляется и скрипт положил бы агента в `/root`;
* после attach включается `RUN` (ctrl+enter): скрипт компилируется на хосте и
  уходит в игру тем же путём, что `wieen exec`;
* статус агента проверяется `QTimer` раз в 2.5 с: если игра закрылась, окно
  само возвращается в `DETACHED`.

Движение. Индикатор вкладок едет к выбранной по `QRectF` с `OutBack` —
с лёгким перелётом. Страница приходит из расфокуса и сбоку: `pos` от
`(±30, 14)` к `(0, 0)`, `QGraphicsBlurEffect` от 16 к 0, вуаль над стеком
гаснет с 0.45. Старая страница скрывается сразу, поэтому смешивать нечего:
новая рождается размытой и чуть в стороне, а не проявляется на месте.
Кнопки рисуются вручную (`SoftButton`) и плавно светлеют под курсором, точка
состояния пульсирует, пока идёт работа. Плашки горячих клавиш, полосы статуса и подписей под кнопками больше нет.
Текст интерфейса — английский; CONSOLE не является отдельной вкладкой.

Ловушки PyQt6, которые стоили времени:

1. **Исключение в слоте убивает процесс.** PyQt6 превращает необработанное
   исключение из слота в `qFatal`, и приложение исчезает без сообщения —
   в логе пусто, `faulthandler` показывает только `abort` из
   `QMessageLogger::fatal`. Поэтому в `main()` стоит свой `App`,
   переопределяющий `notify()`: исключение печатается и живёт дальше.
2. **`QPainter.fillRect(QRectF, QGradient)` валит процесс.** Не abort, а
   самый настоящий segfault в недрах Qt 6.12. Градиент рисуется через
   `setBrush(top); drawRect(...)` — так работает.
3. **У виджета без `sizeHint` нулевая ширина.** `TabBar` рисовал вкладки,
   но в layout получал ширину 0 — на экране их просто не было.
4. **Сигнал из рабочего потока в окно — мина.** Результат фоновой задачи
   приходил `pyqtSignal`, и если окно успевало закрыться, PyQt вызывал
   метод у мёртвой обёртки и падал в `sip_api_get_address`. Теперь поток
   кладёт ответ в `queue.SimpleQueue`, а окно забирает его `QTimer`-ом
   раз в 90 мс — ни одного вызова Qt из чужого потока.
5. **Анимация, пережившая свой объект.** `QGraphicsBlurEffect` удаляется
   вместе со страницей, а `QPropertyAnimation` продолжал на него смотреть.
   Перед `setGraphicsEffect(None)` анимации останавливаются, теряют цель и
   уходят в `deleteLater`.
6. **`pos` внутри `QStackedWidget`.** Страница принадлежит `QStackedLayout`,
   и тот выставляет ей геометрию сам; поэтому после `setCurrentIndex`
   геометрия задаётся руками, а `pos` анимируется от смещения к нулю, и в
   конце страница явно возвращается в `(0, 0)`.

Проверено: окно открывается, вкладки переключаются с движением и блюром,
диалог momentum прогоняет шаги (на подменённом процессе), attach к живому
клиенту показывает уведомление и включает редактор, `RUN` возвращает вывод
в консоль. Восемь прогонов открытия/переключения/закрытия — без падений.

## 17. Рубеж 3: контейнер снимает лимит 280 байт

### Два пути загрузчика

`luau_load` клиента (`0x22e4b72`) на входе сравнивает длину блоба с
`0x118` (280). Это не запрет, а переключатель формата:

* меньше `0x118` — блоб грузится как голый байткод Luau;
* не меньше `0x118` — блоб считается **контейнером** с подписью.

Отсюда и прежнее наблюдение «277 байт грузятся, 280 — уже нет»: на 280
клиент уходил во вторую ветку и отвергал блоб, потому что подписи не было.

Контейнер версии 0, собранный наугад, клиент отверг на живом запуске.
Версия 1 прошла.

### Формат версии 1

```
payload            байткод Luau как есть
pad                0x10 байт
footer             0x18 байт
```

Проверки, которые проходит загрузчик:

```
pad[0x00..0x03] ^ pad[0x08..0x0b] == 0x946ac432
u16(footer[0x00])                == 0xc432
footer[0x02]                     == 0x6a
footer[0x03]                     == 0x01   (версия)
u32(footer[0x10])                == 0x016ac432 ^ 0x74171870
```

Поле, с которым сверяется загрузчик, не зависит от полезной нагрузки:
это метка, сложенная с сидом. Поэтому подпись подходит к **любому**
байткоду, и лимит исчезает целиком, а не сдвигается.

Собирает контейнер `with_container()` в `tools/wieen_compile.cpp` — и для
обычных скриптов, и для каждой части `loadstring`, и для диспетчера.

### Пределы

| предел | значение | где |
|---|---|---|
| один чанк | 4 МиБ | `kPartCap` в компиляторе |
| одно сообщение сокета | 16 МиБ | `MAX_MESSAGE` в агенте |

Скрипт длиннее по-прежнему режется на части и идёт диспетчером
`WIEENLSP`; внутри игры граница «280» больше не участвует.

### Проверено на Infinite Yield

* исходник — 490 225 байт, байткод — **605 731 байт**;
* приходит одним кадром сокета, одним чанком;
* в логе агента — `luau_load returned 0`;
* интерфейс строится: под `RobloxGui` появляется `ScreenGui` со случайным
  именем и **841 потомком**;
* скрипт проходит дальше своих проверок прав, доходит до создания окон и
  колбэков.

### Почему до этого падало на `Players`

Агент одалживал по смещению `lua_State + 0x0c` маленькую маску из
`caps.txt`. Там лежит не маска, а счётчик клиента. Ложная маска попадала
в общий checker прав и отнимала у потока бит `Players` (34) — отсюда
`lacking capability Players` на `Player` и `LocalPlayer`.

Что изменено:

* одолживание `+0x0c` убрано совсем;
* `looks_like_caps()` теперь считает указателем любое значение, которое
  указывает на отображённую память, — маски клиента
  (`0x3e100000000`, `0x303fffffffffff0b`) никуда не указывают, а вот
  поле-указатель раньше затиралось через `~0` и роняло клиент;
* одалживаются настоящие поля проверки: `[[L+0x20]+0x80]`, `[env+0x70]`
  (при нуле — маска по умолчанию `0x703eb90`) и `[env+0x190]`.

После этого IY возвращает `nil` (успех), в логе нет ни одной строки
`lacking capability` после правки.

### Почему интерфейс IY не работал после запуска

Одалживание масок возвращало поля на место сразу после вызова, а IY
создаёт **замыкания, которые живут дольше вызова**: обработчики кнопок,
перетаскивание окон, консоль. Клиент вызывает их позже, и проверка прав
идёт заново.

Проверено на живом клиенте: колбэк `Heartbeat`, созданный чанком,
исполняется и после возврата, но запись `Part.Name` падала
`lacking capability Basic`. Причина — проверка не находит окружение
замыкания и берёт маску по умолчанию `0x703eb90` (там лежал `0`), либо
читает уже возвращённую маску окружения. Поэтому:

* маски окружения (`env+0x70`, `env+0x190`) остаются одолженными на всё
  время жизни процесса — `WIEEN_ENVKEEP=0` возвращает старое поведение;
* маска по умолчанию остаётся одолженной — `WIEEN_DEFKEEP=0` возвращает
  старое поведение.

Маски потока и checker'а по-прежнему возвращаются после вызова.

Проверка после правки:

```
Heartbeat-колбэк: Part.Name = ...          -> ok, без ошибок
execCmd("speed 88") из Heartbeat-колбэка   -> Humanoid.WalkSpeed = 88
интерфейс IY под RobloxGui                 -> 841 потомок, жив
```

### Что осталось закрытым

`workspace.CurrentCamera` — по-прежнему `lacking capability Camera
(Basic)`: это отдельная проверка контекста скрипта, масками её не
открыть. `game.Players.LocalPlayer` и свойства `Player` теперь читаются.

Мелочь для повторных прогонов в одной VM: IY использует глобальную
`currentShade1` раньше, чем определяет её, поэтому второй запуск поверх
первого может упасть на числовом ключе в таблице свойств. Чистая VM —
без проблемы.
